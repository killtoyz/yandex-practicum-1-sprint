# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление датчиками:**

- Пользователи могут регистрировать/добавлять новый датчик в приложении, указав имя, тип, расположение и единицу измерения (POST /api/v1/sensors)
- Пользователи могут получить список всех зарегистрированных/добавленных датчиков (GET /api/v1/sensors)
- Пользователи могут посмотреть информацию по конкретному датчику (увидеть карточку датчика) (GET /api/v1/sensors/{id})
- Пользователи могут изменять данные датчика: имя, тип, расположение, единицу измерения и статус (PUT /api/v1/sensors/{id})
- Пользователи могут удалить датчик из приложения (DELETE /api/v1/sensors/{id})
- Пользователи могут обновить данные датчика вручную, указав показания датчика и его статус (PATCH /api/v1/sensors/Х{id}/value)

- Система позволяет автоматически проставлять служебные поля при создании датчика: статус и показания, при измененнии: дату последнего обновления
- Система хранит каталалог датчиков в БД
- Система проверяет обязательность полей при создании датчика: имя, тип, расположение

**Мониторинг температуры:**

- Пользователи могут просматривать температуру в конкретной комнате (локации) // Тут у меня сразу возник вопрос, сейчас не вижу как решается проблема если эта локация содержит, например 2 датчика?
- Пользователи могут получать температуру конкретного датчика (GET /sensors/{id})
- Система при чтении датчика (GET /sensors, GET /sensors/{id}) обогащает запись актуальными: значением температуры, статусом и датой последнего обновления из сервиса температуры, обращаясь к нему по идентификатору датчика
- Система при недоступности внешнего сервиса возвращет последние сохранённые в БД значения

**Инфраструктурные возможности**

- Система поддерживает healthcheck запросы для проверки рабоспособности сервиса

### 2. Анализ архитектуры монолитного приложения

- Язык: Go
- База данных: PostgreSQL
- Взаимодействие между компонентами: синхронное (роутер - обработчик, обработчик - сервис, обработчик - бд)
	- При недоступности сервисов приложение возвращает данные из БД (Например, температуру датчиков)
	- Цепочка взаимодействий выглядит так: 1. Поступил запрос 2. Приложение принимает запрос 3. Роутер по методу и пути определяет обработчик 4. Обработчик (SensorHandler) читает или изменяет данные в PostgreSQL, а для датчиков температуры дополнительно запрашивает актуальное значение у temperature_service
- Контейниризация: Docker
	- Переменные окружения: DATABASE_URL (адрес БД), TEMPERATURE_API_URL (адрес сервиса)
	- Используется легковесный образ postgres:16-alpine

### **4. Проблемы монолитного решения**

**Отказоустойчивость**

- Сейчас используется одна БД на все домены. Это единая точка отказа приложения. При микросервисном подходе можно было бы выделить отдельные БД под каждый сервис
- Если ПО по каким-то причинам "Упадёт", то станут недоступны все функции приложения. При микросервисном подходе "падала" бы только часть ПО и часть функций осталась бы доступна
- Т.к. планируется расширение, то каждое новое добавление устройств будет изменять логику всего приложения. Каждый новый тип устройств = новая внешняя интеграция и новый источник отказов внутри общего монолита.

**Масштабирование**

- Если в будущем количество пользователей приложения резко возрастет (а это планируется из условия задания), то все обращения пользователей будут поступать к одному серверу. Можно увеличить мощности сервера или запускать монолит на нескольких серверах с добавлением балансировщика и общей БД.
	- Если большая часть нагрузки на ПО будет, например, из-за использования пользователями функций отопления, то не получится масштабировать только эту часть ПО, при этом нагрузка из-за использования функций умного дома будет незначительной. Таким образом, монолиту недоступно избирательное масштабирование отдельных сервисов (функций)

**Деплой**

- При реализации поддержки новых устройств (и их API) или обновлений отдельных функций придётся обновлять целиком все приложение
- Если реализация поддержки новых устройств (умного дома и т.д.) потребует введения новых технологий в билд приложения, то придётся добавлять установку отдельных зависимостей в докерфайл или брать другой базовый образ, что может вызвать проблемы

**Организация разработки**

- Сейчас несколько разработчиков работают в одной кодовой базе, что будет постоянно вызывать конфликты при мерджах

# Задание 4. Создание и документирование API

### 1. Тип API

**REST-синхронное взаимодействие**
Все события, которые инициируются пользователем - синхронные, т.к. пользователю нужен немедленный ответ.
Запросы маршрутизируются непосредственно в микросервис, ответственный за этот функционал.

**AsyncApi-асинхронное взаимодействие**
Все события, которые инициируются системно - асинхронные, т.к. это повышает отказоустойчивость системы. Пример такого события, телеметрия (мониторинг устройств).

**Как работает гибридное взаимодействие**

Показатели устройств накапливаются асинхронно и сохраняются в БД сервиса мониторинга. Пользователь отправляет синхронный запрос на получение показателей устройства.

Когда пользователь отправляет запрос, то читаются последние опубликованные данные, которые сервис мониторинга отдаёт из своей БД.

1. Это сохраняет "текущую" логику как было в монолите, т.к. тоже отдавались данные из БД при недоступности сервиса
2. Данные могут оставать от реальных
3. Это повышает отказоустройчивость всей системы

**Взаимодействие с микросервисами и между ними**

1. Перед микросервисами стоит API-шлюз (API Gateway),который маршрутизирует запросы пользоваля в нужный микросервис (также может понадобиться Service Registry). На диаграммах это не выделено, но имеется ввиду. На диаграммах не выделял, т.к. этого не запрашивалось по ДЗ.
2. Между микросервисами для асинхронного взаимодействия должен быть реализован единый брокер сообщений. Каждый сервис-издатель владеет своими топиками. Любой желающий может подписать на конкретный топик. Также не выделено на диаграммах.
